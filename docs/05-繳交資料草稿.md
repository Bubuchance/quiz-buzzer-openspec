# 05 繳交資料草稿（Google 表單用）

> 以下是依作業說明「內容包含系統簡述、GitHub Repo 與影片連結、AI 對話紀錄、實作方法與心得、小組分工表」整理的草稿。
> **心得與分工請組員用自己的話改寫**，這部分是評分的「說明完整度、組員貢獻程度」。

## 系統簡述（可直接用）

課堂搶答系統透過 Google Sheets API 直接串接老師雲端上的 Guided Notes（依「題號」「作答」欄位標題動態定位，標題列位置與欄位順序不限；題組在作答欄以（1）（2）標示），開啟搶答後各組學生以組別為單位送出答案，伺服器依收到先後判定每題最快的組別。活動分為準備中、搶答中、已結束三個階段，所有頁面透過 WebSocket 即時同步；搶答期間學生看不到其他組作答，老師即時看到全部。結束後系統直接把成功答案寫回雲端試算表的作答格，並可匯出 CSV。額外功能：題組、CSV 匯出、公平順位機制（有效時間 = 收到時間 + 已成功題數 × 延遲量）。創意功能：倒數計時自動結束、老師標記對錯與計分板、學生端作答進度提示。功能與 SpecKit 組對齊。技術：Python FastAPI、WebSocket、gspread（Google Sheets API，服務帳號授權、金鑰不進 repo）、原生 HTML/CSS/JS，94 個自動化測試。

## 實作方法（可直接用，再補充）

1. **Explore**：把作業需求整理成 12 條已確認規則與 11 條合理預設（例如佔位符格式、匯入匯出方式），寫成 13 個驗收情境。
2. **Propose**：產生 proposal（為什麼／做什麼）、5 個能力的 spec（25 條 Requirement、53 個 WHEN/THEN 情境）、design（技術選擇與替代方案）、tasks（8 組 23 項，每項附驗證方式），並以 `openspec validate --strict` 檢查格式。
3. **Apply**：依 tasks 逐項實作，每組任務完成就跑測試，前端完成後用瀏覽器以老師＋2 組實際跑完整流程。
4. **Verify**：逐條對照 Requirement 與 Scenario，找出 3 個沒測到的情境補測試；發現 design 與實作不一致之處回寫文件。
5. **Sync／Archive**：把 change 的 spec 合併為 `openspec/specs/` 主規格，再把 change 封存；最後把專案慣例寫進 `openspec/config.yaml`。
6. **與 SpecKit 組對齊（第二個 change）**：收到 SpecKit 組的功能對齊清單後，依老師流程圖回到 Explore 開新的 change `align-with-speckit`，在獨立分支完成，以 REMOVED／MODIFIED／ADDED 記錄規格變更，再以 PR 合併。
7. **依課程公告改為直接串接 Google Sheets（第三個 change）**：老師公告不能下載 xlsx 離線處理，開新的 change `connect-google-sheets`，改用 Google Sheets API ＋ 服務帳號直接讀寫雲端試算表。
8. **人工驗證**：組員依 `docs/04-人工驗證清單.md` 操作並記錄。

## 心得（請改寫成自己的話，以下是可參考的觀察）

- 先寫 spec 讓「學生看不到別組」這種容易漏的規則變成可測試的情境，AI 實作時不會忘記。
- 單元測試全過不代表系統能用：AI 寫的測試用 TestClient 模擬 WebSocket，真的啟動伺服器時卻因為少裝 `websockets` 套件而連不上，靠瀏覽器實測才發現。所以人工／實機驗證很必要。
- 作業禁止寫死儲存格，所以改用「題號」「作答」欄位標題動態定位；第一版我們自己設計了 {{n}} 佔位符，和 SpecKit 組對齊後改成他們的格式，也體會到兩組要先講好規則。
- 一開始為了避免處理金鑰而選擇下載／上傳 xlsx，但課程公告要求直接串接雲端。改成服務帳號後，關鍵是把金鑰放在 `.gitignore` 排除的資料夾、用環境變數指定路徑，既能串接又不洩漏金鑰。需求會變，用 OpenSpec 開新 change 記錄「為什麼改」很有幫助。
- 兩組對齊時，OpenSpec 的 delta spec（MODIFIED／REMOVED／ADDED）把「改了什麼、為什麼改」記錄下來，比直接改程式清楚。
