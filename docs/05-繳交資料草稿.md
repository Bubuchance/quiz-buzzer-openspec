# 05 繳交資料草稿（Google 表單用）

> 以下是依作業說明「內容包含系統簡述、GitHub Repo 與影片連結、AI 對話紀錄、實作方法與心得、小組分工表」整理的草稿。
> **心得與分工請組員用自己的話改寫**，這部分是評分的「說明完整度、組員貢獻程度」。

## 系統簡述（可直接用）

課堂搶答系統讓老師匯入 Google Sheets 格式的 Guided Notes（以 `{{題號}}`、`{{題號-小題}}` 佔位符標記填空格，系統掃描所有工作表動態辨識，不依賴固定儲存格），開啟搶答後各組學生在自己的瀏覽器以組別為單位送出答案，伺服器依收到先後判定每題最快的組別。搶答期間學生看不到其他組作答，老師即時看到全部；所有頁面透過 WebSocket 即時同步活動階段。結束後老師可把成功答案寫回原 Guided Notes 的填空格並匯出 CSV。額外功能：題組（須同時送出）、CSV 匯出、公平模式（時間窗內成功題數較少者優先）、成功題數統計。技術：Python FastAPI、WebSocket、openpyxl、原生 HTML/CSS/JS，54 個自動化測試。

## 實作方法（可直接用，再補充）

1. **Explore**：把作業需求整理成 12 條已確認規則與 11 條合理預設（例如佔位符格式、匯入匯出方式），寫成 13 個驗收情境。
2. **Propose**：產生 proposal（為什麼／做什麼）、5 個能力的 spec（25 條 Requirement、53 個 WHEN/THEN 情境）、design（技術選擇與替代方案）、tasks（8 組 23 項，每項附驗證方式），並以 `openspec validate --strict` 檢查格式。
3. **Apply**：依 tasks 逐項實作，每組任務完成就跑測試，前端完成後用瀏覽器以老師＋2 組實際跑完整流程。
4. **Verify**：逐條對照 Requirement 與 Scenario，找出 3 個沒測到的情境補測試；發現 design 與實作不一致之處回寫文件。
5. **Sync／Archive**：把 change 的 spec 合併為 `openspec/specs/` 主規格，再把 change 封存；最後把專案慣例寫進 `openspec/config.yaml`。
6. **人工驗證**：組員依 `docs/04-人工驗證清單.md` 操作並記錄。

## 心得（請改寫成自己的話，以下是可參考的觀察）

- 先寫 spec 讓「學生看不到別組」這種容易漏的規則變成可測試的情境，AI 實作時不會忘記。
- 單元測試全過不代表系統能用：AI 寫的測試用 TestClient 模擬 WebSocket，真的啟動伺服器時卻因為少裝 `websockets` 套件而連不上，靠瀏覽器實測才發現。所以人工／實機驗證很必要。
- 作業禁止寫死儲存格，促使我們設計佔位符規範，反而讓匯入匯出邏輯更簡單、可換任何範本。
- 不直接寫回 Google Sheets 是刻意取捨：需要 OAuth 金鑰會違反不可洩漏金鑰的規定，下載再匯入雖多一步但安全。
